# Release-to-Docs Audit: `ui_locales` support (v1.0.1)

## Summary

- Release: v1.0.1
- Commit: 86368db4a
- Documentation coverage: partial
- Potential product issue: yes
- Runtime verification: pending
- Recommended action: technical review before documentation updates

**Bottom line:** The server now accepts `ui_locales` and passes it on to the login page. But the login app that ships in v1.0.1 appears not to read it, so the sign-in screen's language probably does not change. No v1.0.1 page explains the parameter; it is only mentioned once, in an example list. Coverage is partial: mentioned, not explained, not documented well enough for developers to use. Before writing docs, someone needs to confirm the end-to-end behaviour (question Q1 in section 5).

**Scope:** Commit `86368db4a` ("Add ui_locales support", 5 files, +29 lines). All code and docs were read at the `v1.0.1` tag (`2e745612817986330cadc3767935e929b26ff46c`), not the working branch. Line numbers refer to files at that tag.

### What the login UI (Gate) does with it (verified by reading code, not by running it)

| # | Fact | Evidence |
|---|---|---|
| F10 | Gate's own i18n setup starts in `en-US`. It only switches when the flow's `meta.i18n.language` says so. It never reads `ui_locales` from the URL. | `frontend/apps/gate/src/hocs/withI18n.tsx:20-31, 45, 63-64` |
| F11 | Gate wraps the app in `ThunderIDProvider` from `@thunderid/react`, pinned to `1.0.3` in `pnpm-workspace.yaml:39`. | F12 | Gate passes `config.sdk` from its runtime config into the provider. The v1.0.1 source tree contains no runtime config that sets `preferences.i18n.urlParam` to `ui_locales`. | `frontend/apps/gate/src/hocs/withConfig.tsx:15-22`; no `urlParam` or `ui_locales` hits under `frontend/apps/gate` |
| F13 | No v1.0.1 frontend code anywhere references `ui_locales`. The installed `@thunderid/react@1.0.3` build only lists `ui_locales` in its OIDC discovery type file. | `git grep` on `frontend/`; `grep` of the installed SDK packages |

**Inference (needs runtime check):** With a default v1.0.1 setup, `/oauth2/authorize?...&ui_locales=fr` sends the browser to the Gate login page with `ui_locales=fr` in the URL. Gate then most likely shows the language from the cookie, the browser, or `en-US`, not French. So the release delivers the backend half of the feature, and the end-to-end effect is unconfirmed.

Note on F11: the SDK evidence comes from the locally installed `@thunderid/react@1.0.3` package, which matches the v1.0.1 catalog pin. It was not re-downloaded from the registry.

## 4. Recommendations (not facts)

Do these after Q1 is answered.

1. **`docs/content/guides/protocols/oauth-oidc/openid-connect.mdx`.** Add a `ui_locales` row to the "Authentication Context Parameters" table (around line 60): "Preferred languages for the sign-in UI, space-separated BCP 47 tags in order of preference. Forwarded to the login page." Link to the localization guide. If Q1 confirms the Gate ignores it, say so plainly (for example: "Accepted and forwarded; the built-in login app uses the `lang` parameter…") rather than implying it works.
2. **`docs/content/guides/i18n/localization.mdx`.** Add a "How the Display Language Is Selected" section before "Language Matching" (line 69). Give the actual order: `preferences.i18n.language`, then the URL parameter (`lang` by default, configurable through `urlParam`), then the stored cookie, then the browser language, then `fallbackLanguage`. State where `ui_locales` fits. Cross-link `sdks/javascript/apis/configuration.mdx#internationalization-preferences`.
3. **`api/oauth2.yaml`.** Add a `ui_locales` query parameter to `/oauth2/authorize` (after `prompt`, around line 150) and a `ui_locales` property to `PARRequest` (around line 774). Add `claims_locales` too (G7).
4. **`docs/content/guides/protocols/oauth-oidc/par.mdx`.** Optionally add one line saying that any parameter accepted by `/oauth2/authorize` (including `ui_locales` and `claims_locales`) can be pushed. A dedicated row isn't needed.
5. **`docs/content/sdks/react-router/apis/protected-route.mdx:138`** (and the `version-v1.0.x` copy). No change needed. Optionally link `ui_locales` to the OIDC page once item 1 exists.
6. **Product, not docs:** if the intent was for the login UI to follow `ui_locales`, either set Gate's `preferences.i18n.urlParam` to `ui_locales` or have the backend also send `lang`. Separately, add a PAR-path unit test for `par/service.go:145`. Neither is part of this audit's scope.

**Open questions:**

1. **Q1, runtime:** On a v1.0.1 server with an `fr` translation added, does `/oauth2/authorize?...&ui_locales=fr` show French on the login screen? Compare with `&lang=fr`. Check both the standard and PAR flows.
2. **Q2:** Do any packaged Gate deployment configs outside the source tree (Docker image, Helm values, generated `config.js`) set `sdk.preferences.i18n.urlParam`?
3. **Q3:** Is support for multiple values intended (OIDC allows `"fr-CA fr en"`)? The backend forwards the raw string, and the SDK would treat it as one language tag.
4. **Q4:** Was it intentional to leave `ui_locales` out of `runtimeData`, so that server-rendered flow content and notification emails don't use it?
5. **Q5:** Is a `ui_locales_supported` entry in discovery planned? That decides whether `server-metadata.mdx` needs an update.
